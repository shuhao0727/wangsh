### 2.3 索引覆盖情况

#### ❌ 严重缺失的索引

```sql
-- 1. 会话历史查询（最高优先级）
CREATE INDEX ix_conversations_session_created
ON znt_conversations(session_id, created_at DESC, id DESC);

-- 2. 深度分析时间范围扫描
CREATE INDEX ix_conversations_agent_time
ON znt_conversations(agent_id, created_at, id)

-- 3. 小组讨论消息分页
CREATE INDEX ix_group_messages_session_created

-- 4. 用户会话列表
CREATE INDEX ix_conversations_user_agent_time
ON znt_conversations(user_id, agent_id, created_at DESC);

-- 5. class_name 过滤优化
CREATE INDEX ix_users_class_name
ON sys_users(class_name) WHERE class_name IS NOT NULL;
```

### 2.4 数据冗余问题

**user_name / agent_name 快照冗余**
- **占用**：每条消息多 300 bytes
- **优点**：历史回放不依赖外键，防止删除导致数据丢失
- **缺点**：用户/智能体改名后数据不一致
- **建议**：保留快照，但查询时优先 JOIN 获取最新名称

## 三、数据访问模式分析

### 3.1 查询清单与性能

| 查询类型 | 频率 | 当前耗时 | 优化后 | 瓶颈 |
|---------|------|---------|--------|------|
| 会话列表 | 每分钟数十次 | 100-500ms | 10-50ms | 窗口函数 + 视图 JOIN |
| 会话详情 | 每分钟数十次 | 10-50ms | 5-20ms | 缺少复合索引 |
| 深度分析 | 每小时数次 | 5-30s | 3-20s | O(n²) 聚类算法 |
| 统计查询 | 每小时数次 | 100-500ms | 20-100ms | 大范围扫描 |
| 批量导出 | 每天数次 | 500ms-5s | 300ms-3s | 多会话聚合 |

### 3.2 识别的 N+1 问题

✅ **已避免**：
- 会话列表使用窗口函数预加载最后消息
- 视图设计预关联 users 和 agents

⚠️ **潜在风险**：
- 深度分析中的教师锚点匹配（O(n*m) 复杂度）
- 事件质量分类的逐条处理

### 3.3 并发风险点

| 场景 | 风险等级 | 当前机制 | 建议 |
|------|---------|---------|------|
| 会话创建 | 🟢 低 | UUID 天然避免冲突 | 确认唯一索引 |
| 消息追加 | 🟢 低 | 自增 PK + 时间戳排序 | 无需额外锁 |
| 分析任务并发 | 🟡 中 | 无锁，纯读 | 添加 Redis 缓存 + Celery 队列 |
| 视图查询 | 🟢 低 | PostgreSQL MVCC | 注意连接池耗尽 |

## 四、缓存与会话管理

### 4.1 Redis 键模式清单

| 键模式 | 用途 | TTL | 数据结构 |
|--------|------|-----|---------|
| `auth:session:uid:{user_id}` | 用户会话 nonce | 动态 | String |
| `wangsh:dify:concurrency:{key}` | Dify 并发租约 | 配置 | Sorted Set |
| `debug:session:{session_id}` | PythonLab 会话元数据 | 1800s | Hash |
| `articles:p:list:{params}` | 文章列表缓存 | 300s | String (JSON) |
| `rl:{key}` | 限流计数 | 动态 | String |

### 4.2 会话状态机

#### Dify 智能体流式会话
```
[未获取租约] → acquire()
       ↓
[租约已获取] → 后台续租循环 (interval = lease_seconds / 3)
       ↓
SSE 流式传输 (逐 chunk 检查租约)
       ↓
[租约丢失 ❌] 或 [流完成 ✓] → release()
```

#### PythonLab 调试会话
```
PENDING → STARTING → READY → ATTACHED → RUNNING/STOPPED
                                    ↓
                          TERMINATING → TERMINATED
```

### 4.3 发现的问题

| 问题 | 风险等级 | 影响 |
|------|---------|------|
| 缓存穿透风险 | 🟡 中 | 异常降级为 None，无法区分"不存在"和"Redis 不可用" |
| PythonLab 会话泄漏 | 🟢 低 | `debug:user:{user_id}:sessions` Set 积累脏数据 |
| Dify 租约续租无容错 | 🟡 中 | Redis 抖动可能中断流式响应 |
| 状态不一致 | 🟢 低 | Redis 投影 vs DB 权威记录延迟 |
| 电路断路器无分布式 | 设计限制 | 多 worker 各自独立熔断 |
| 缓存击穿风险 | 🟢 低 | 热点键同时过期，并发回源 |

### 5.2 数据增长预测

**典型教学场景**（6 班级 × 240 学生 × 10 智能体）

| 年份 | 对话记录 | 分析记录 | 总空间 | 实际需求（含索引） |

| 第 1 年 | 300 MB | 39 MB | 340 MB | **~450 MB** |

| 第 3 年 | 900 MB | 117 MB | 1020 MB | **~1.3 GB** |

**告警阈值建议**：
- ⚠️ 警告：500K 条对话（~500 MB）
- 🔴 严重：1M-5M 条对话（1-5 GB）
- 🚨 紧急：&gt;5M 条对话（&gt;5 GB）

### 5.3 归档方案设计

#### 三层数据管理
```
热数据（< 3 个月）
    ↓ 自动归档
温数据（3-12 个月，标记 is_archived=True）
    ↓ 自动迁移
冷数据（> 12 个月，迁移到 *_archive 表）
```

#### 实施步骤

**阶段 1：添加归档字段**（1 周）
```sql
ALTER TABLE znt_conversations ADD COLUMN is_archived BOOLEAN DEFAULT FALSE;
ALTER TABLE znt_conversations ADD COLUMN archived_at TIMESTAMP WITH TIME ZONE;
CREATE INDEX ix_conversations_archived ON znt_conversations(is_archived, created_at);
```

**阶段 2：创建 Celery 定时任务**（2 周）
```python
@celery.task
def archive_old_conversations():
    """每周归档 90 天前的对话"""
    cutoff = datetime.utcnow() - timedelta(days=90)
    db.execute(
        "UPDATE znt_conversations SET is_archived=TRUE, archived_at=NOW() "
        "WHERE created_at < :cutoff AND is_archived=FALSE",
        {"cutoff": cutoff}
    )
```

**阶段 3：改造查询层**（1 周）
```python
# 默认过滤已归档数据
query = select(Conversation).where(Conversation.is_archived == False)
```

**预期效果**：
- 主表数据量减少 **60-70%**
- 查询性能提升 **40-60%**
- 磁盘空间节省 **30-50%**
- 备份时间缩短 **50%**
