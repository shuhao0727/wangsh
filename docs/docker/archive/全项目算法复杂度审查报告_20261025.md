### 1.2 三句话结论

> **① 最大的问题不是算法复杂度，是 DB 往返次数。** 全项目没有找到 O(n³) 或指数级算法（前端唯一疑似重型的 `tidy.ts` 是死代码）。但存在 **5 处「O(n) 次 DB 往返」的循环**（P0-2/4/5/9 + P1 若干），在 3000 行规模下变成 6,000~30,000 次网络往返。

> **② 有一个真实存在的 O(n²) 且代价惊人：** 选课工作簿确认接口因为 `load_workbook(read_only=True)` + 逐格 `ws.cell()`，**3000 人需要约 13 分钟**。改一个参数（`read_only=False`）降到 0.002 秒——**快 40 万倍**。这是本次审查最值钱的发现。

> **③ 前端基本健康，但有一个"白跑计算"值得修。** P0 = 0。绝大多数表格走服务端分页（默认 20 行），收不到大数据集；只有 2 处会把全量数据灌进浏览器。
> 真正可修的是一个浪费：`useBeautifyFlow` 在用户拖拽节点时触发完整图布局（wasm dot + O(E²) 交叉计数），但产物只喂给一个**没打开就不渲染**的 Tab——**用户没看，计算照跑**。修法约 5 行（deps 换成已存在的 `semanticKey`）。

### ⚠️ P0-6 的可达性说明（不要误判为线上热点）

审查员用 grep 核实后**修正了入口表述**，这一点必须写清楚，否则会误导排期：

- **Celery 路径是唯一正式入口**（正常触发）
- `classroom.py:423 analyze_fill_blank_stats` 在 `api/endpoints/classroom/*` **没有对应路由，当前不可达**
- 但 `analysis_status` / `analysis_result` 已在 `admin.py:293-294` 对外暴露 —— **一旦把路由接回来，就会变成请求内同步 sweep**

所以 P0-6 的定性是「**埋着的雷**」而不是「正在烧的火」。修复它的优先级低于 P0-1~P0-5，但成本低（截断候选数 + `asyncio.timeout`），建议顺手修掉，避免将来接路由时炸。

**同时这条报告了一个正面结论**：群组讨论的四条分析路径全是「N 个对象 → 1 次 LLM」，**完全做对**，可以作为改造 P0-6 的现成范本。

### P0-3 的铁证（这条最反直觉，值得单独说）

`read_only=True` 的 O(n²) 是 openpyxl 的实现细节：`ReadOnlyWorksheet._get_cell` 每次都新建 `WorkSheetParser` **从第 1 行重新解析整个 sheet XML**。

cProfile 数据（300 人工作簿）：

| 指标 | 次数 |
|---|---|
| `ws.cell()` 被调用 | **2,198 次**（线性，符合直觉） |
| 底层 `openpyxl.worksheet._reader.parse_cell` 被调用 | **2,423,154 次**（平方，真正原因） |

同一份文件、同一次请求内的对照：

| 读取方式 | 耗时 |
|---|---|
| `read_only=True` + 逐格 `ws.cell()` | **15.66 s** |
| `read_only=False` + 逐格 `ws.cell()` | **0.021 s** |

**相差 745 倍，只改一个布尔参数。** 而且同一文件内 `parse_course_selection_workbook` 用的正是 `read_only=False`（线性）——**两条读取路径一条线性一条平方，这是最容易被漏掉的地方**。修复时照着同文件的另一条路径改即可。

## 5. 系统性结论（比单点问题更重要）

### 5.1 每个请求先付 3~4 次 DB 往返

`03` 报告指出：**任何通过鉴权的请求，在进入 handler 之前已经付了 3~4 次 DB 往返**（token 校验 + 用户加载 + 权限检查 + 会话状态）。所以：
- handler 里再查 20 次 = 单请求 24 次往返
- 判 P0/P1 时必须把这个基线算进去

### 5.2 代码里「批量」和「逐行」并存，说明不是不知道，是没一致执行

同一份代码里：
- `import_export.py` 的**预校验**按 500 分块（`_validate_student_identities:370-392`、`_common.py:101-110`、`locking.py:20-40`）—— 做得好
- 但**写入阶段**退化成逐行 `guard` + `upsert` —— 前后不一致

同理 `course_selection_workbook.py` 里 `parse_course_selection_workbook` 用线性读取，`read_course_selection_workbook_expectation` 用平方读取。

**这类"同一文件内两种写法"是最容易修也最容易漏的。**

### 5.3 `statement_timeout` 拦不住这类问题

`db/database.py:35` 设了 `statement_timeout`，但 **P0-2 / P0-4 / P0-5 / P0-9 都是「N 条快 SQL 累加」**——每条都远低于 timeout，累加却超时。

**数据库保护机制对这类问题是失效的**：最终只能靠网关 30s 超时把请求截断成 502，用户体验是"点了导出，转圈 30 秒后报错"，而不是"慢但成功"。

### 5.4 并发原语缺失：`asyncio.gather` 全仓库 0 命中

这是本轮审查最值得单独讲的横切面（已验证）：

```
asyncio.gather            0 命中
asyncio.Semaphore         1 处（typst 编译，不在本范围）
asyncio.timeout/wait_for  27 处
```

意味着：**所有阻塞式 LLM 调用都是裸串行，没有任何并发限流或总预算超时。**
配合三处 串行 × N（课堂分析 N_agents / 批量画像 N_users / 交卷评分 Q 道题），就是 P0-1、P0-6、P0-8 的共同根因。

**这不是"某个函数写错了"，是缺少一个模式。** 修单点只能治标；建议加一个统一封装：`gather_with_limit(limit, timeout)`，然后逐个改造。

**正面对照**：群组讨论的四条分析路径全是「N 个对象 → 1 次 LLM」，完全做对——说明团队知道正确做法，只是没有一致执行（这和 §5.2 的结论一致）。

### 5.5 索引结论：不需要大改

`03` 报告核查 57 个 FK / 152 个迁移索引 / 14 个模型索引后结论：
- **确需补的复合索引只有 2 个**：`znt_assessment_sessions(config_id, status)`、`xbk_selections(year, term, course_code)`
- **看似缺失但不应建的有一批**（无查询调用），过度索引反而增加写放大
- 已有 2 个等价索引并存需清理（`sys_users.class_name`）

**索引不是本项目的瓶颈，DB 往返次数才是。**

## 6. 建议的修复顺序

**原则：先修「改一行、收益 1000 倍」的，再修「改架构」的。**

| 顺序 | 项 | 工作量 | 收益 | 风险 |
|---|---|---|---|---|
| **1** | **P0-1**：`user_ids` 加 `max_length=200` | **1 行** | 60 人超时 → 有界；堵住 1.7 小时的必然失败 | 极低 |
| **2** | **P0-2**：用户导入加 `file.read(MAX_BYTES)` + 行数上限 | **几行** | 堵住无上限入口（当前理论 10 万行） | 极低 |
| **3** | **P0-3**：`read_only=True` → `False`（或改 `iter_rows` 单遍扫描） | **1 行** | 3000 人 **13 分钟 → 0.002 秒** | 极低（同文件已有 `read_only=False` 先例） |
| **4** | **P0-4 / P0-5 / P0-9**：导入导出批量化（500/批） | 中（各 1 个函数） | 往返 O(n) → O(n/500) | 中（需测 upsert 语义） |
| **5** | **P0-6**：候选智能体截断到常数 + `asyncio.timeout` 总预算 | 小 | 30 分钟 → 30 秒 | 中（改并发） |
| **6** | **P0-7 / P1-8**：统计下推 SQL 聚合 | 中 | 75MB → 几十行 | 中（要对账） |
| **7** | P1-1 / P1-2 / P1-11：零散批量化 | 中 | 520/120 次 → 几次 | 低 |
| **8** | 前端 P1-12 / P1-13：改服务端分页 | 中 | 首次打开快 | 低 |

> **第 1、2、3 项合计改动不超过 10 行，几乎零风险，可立刻做。**
> 其中第 3 项（`read_only`）收益最大但**只影响一个确认接口**；第 1、2 项是"堵住必然失败/无上限入口"，影响面更广。

## 8. 负结论（查过确认没问题，避免后人重复投入）
