## 〇、本文件要解决什么

原计划是一份**流程框架**，但它是在**尚不知道真实执行会碰到什么**的情况下写的。
`项目整体情况与启动` 会话（下称"原会话"）已经**按原计划实际跑了 S1**，产生了真实数据：

**本文件不替代原计划**，而是在其基础上订正。原计划中被确认有效的部分继续沿用。

### 1.2 原会话踩到的坑（都是原计划没预见到的）

#### 坑 1：验证 Agent 自建"通过"标准，复核 Agent 推翻后才知道标准不够

验证 Agent 对 S1-1 的检查项是：
> 三种模式产出非空文件 → `pg_restore --list` 可读 → full 恢复到新库行数一致 → 失败路径有非零退出码

复核 Agent 在此基础上补测了**检查项清单之外的场景**（16MB 中文/emoji、data 模式恢复到非空库、
`--clean` 的清理边界），才挖出真缺陷。

**原计划的问题**：§二 规则 2 只要求"记录检查项"，**没要求检查项清单在验证开始前冻结并由主控审核**。
结果是验证 Agent 的自由度决定了验证的深度，复核 Agent 能不能发现问题变成了运气。

**修正**：新增 **规则 8：检查项清单前置冻结**。每级开始前，检查项清单（断言 + 预期结果 + 证伪路径）
必须写入验证报告草稿并 **commit 到工作树**，之后不得修改；发现新检查项只能**追加并标注 `新增于复核阶段`**，
不得删除或弱化原检查项。

#### 坑 2：复核 Agent 的结论本身也带前提，主控差点直接采信

复核 Agent 报告 "data 模式恢复会静默失败"，主控第一次复现时（空表）**没能复现**，
按它的描述精确构造（表里已有数据）才复现成功。

**原计划的问题**：规则 4 只约束"结论"的措辞，没约束**复核 Agent 报告必须附带最小复现步骤**。
如果主控没有二次复现，S1-1 会被写成一个"空表也会失败"的错误结论，修复方向会跑偏。

**修正**：新增 **规则 9：复核结论附最小复现**。复核 Agent 的每条"新问题"必须给出：
最小复现命令 + 预期错误输出 + 实际输出。主控对每条新问题**必须亲自复现一次**才算生效。

#### 坑 3：修复引入了自身回归，主控没有第一时间发现

原会话改 `restore-db` 后，"full 备份被误判成 data 模式而拒绝"——
因为 TOC 正则 `^[0-9].*TABLE public\.` 多了一个点号，匹配不到 `TABLE public t1`。
这个回归**是主控后来重跑全场景时才撞上的**，不在预设检查项里。

**原计划的问题**：规则 5 说"回归测试"，但没写"**修复任何代码后，必须重跑该级全部检查项，
不只是重跑修复项**"。原计划把"修复"和"验证"当成两个阶段，实际上修复会把已验证的项打回未验证。

**修正**：规则 5 补充：**修复即回归**——任何代码改动后，该级所有检查项全部重跑一次，
结果以重跑为准，旧结论作废。

#### 坑 4：S1-3 的表数在两次执行中不一致（54 vs 55），没有核对

- TEST_STATUS:14 记录 S1-3 空库迁移得到 **54 张表**
- 原计划 S2-1 检查项写的是**"断言 55 张表全部建立"**

55 这个数字有出处吗？原计划没说明。如果 S2-1 真的断言 55 就会失败，
而如果实际就是 54，说明原计划写数字时没有核对。**这是一个会让 S2 一开局就卡住的隐患。**

**修正**：所有"数量类断言"必须写出来源（`alembic heads` 输出、`pg_class` 查询、`citemgr` 统计），
并在验证开始时实测一次作为基线。基线未取得前，此项状态只能是"未验证"。

#### 坑 5：未提交改动的验证方式在原计划里写得太粗

原计划 §四 对 6 个未提交文件的验证方式是：
> `_security.py` → 4 种 CORS 写法启动测试 + 空值启动

当前工作区实际是 **17 个未提交文件**（13 个已修改 + 4 个新增未跟踪），原计划写的是"6 个核心文件"，
其余被归入"S3/S4/S5 合并"。实际代码审查发现：

- `_security.py` 用 `Annotated[List[str], NoDecode]` 关闭 pydantic-settings 的 JSON 预解码；
- `session_guard.py` 把拒绝原因从硬编码改成 `_rejected(user_id, reason)`，**并加了 `logger.info`**；
- `stream_session.py` 错误帧新增 `reason` 字段；
- `start-dev.sh` 的改动（+71/−12）涉及 Docker 容器操作，是**S3 级**（误杀开发栈容器）。

**原计划的问题**：把 `_security.py` 判为 S3、`session_guard.py` 判为 S6，但没审查这些改动的
**相互依赖**——`stream_session.py` 的 `reason` 依赖 `session_guard.py` 的 `_rejected()` 返回值，
`useAdminSSE.ts` 依赖错误帧里的 `reason` 字段。**这是三个文件的链式改动，必须作为一个整体验证，
不能分到 S3/S4/S5 三个级别去验。**

**修正**：新增 **规则 10：链式改动作为单一验证单元**。存在调用/数据依赖的改动文件必须同批验证，
可以跨越 S 级标签（以链路中最高的级别为准），但不能拆开到不同级别分别判定。

#### 坑 6：S1-4 的证据来源违反了自己的规则

原计划规则 2 明确"不得仅以代码检索作为验证依据"，但 S1-4 的验证方式是：
> "代码检索确认 stub 已删 + 相关接口在无 LLM 配置时返回明确错误"

后半句是实例验证，前半句是代码检索。TEST_STATUS:15 的记录也是"全仓扫描无残留" + "实例调用抛 ValueError"。

**原计划的问题**：规则 2 说"任何条目不得仅以本地单元测试通过作为验证依据"，
但没禁止"代码检索"作为**部分**依据。如果按字面执行，任何含代码检索的条目都不合规；
如果按实际执行，规则就形同虚设。

**修正**：规则 2 增加明确分类：
- **代码检索**（`rg`、`grep`）只能作为"**确认删除**"的证据，不能作为"**行为正确**"的证据；
- 条目的"行为正确"必须由至少一个**实例检查项**覆盖；
- 纯删除类条目（如 S1-4 删 stub）的"确认删除"由代码检索 + 一个**运行时无残留**检查项共同构成。

#### 坑 7：原会话在 S1 中途改了 TEST_STATUS，但没改计划

TEST_STATUS:12 已经被覆盖过一次（复核前后内容不同），现在有 13 行 S1 记录。
原计划说"每级产出验证报告"，但实际把内容写进了 TEST_STATUS 的同一节里，
**复核 Agent 的原始证据与主控的最终判定混在一起**。

**修正**：规则 4 补充：验证报告的**原始证据**与**最终判定**必须分两个文件/两个区块，
判定只能引用证据，不能改写证据。

#### 坑 8：清理不彻底与"软删除"语义

原会话明确记录：测试账号 id=57、58 是**软删除**（`is_deleted=t`、`active=f`），仍在开发库里。
原计划 §五"不会做"里写"不触碰开发栈容器"，但**已经在开发库里留了测试数据**。

**修正**：规则 6 补充：在开发栈里创建的任何测试数据，必须给出**清理确认结果**（查询证据），
软删除必须**显式说明**并征得同意，不能默认"软删除 = 已清理"。

## 二、原计划规则逐条审核

### 2.1 规则 1：分级驱动 —— ✅ 保留，补一处

**保留**：S1→S7 固定顺序、同级内按"影响面 × 复现概率"排序、每级出报告才能进下一级。

**补充**：
- 增加"**同级内串行**"约束。原计划只说"同级内按排序"，但原会话实际是 S1-1、S1-2、S1-3… 逐项串行跑的，
  没有并行。串行是对的——因为 S1-2 往开发库造了账号、S1-5 起了 D1 栈，并行会互相污染。
- 原计划的"同级别内并行多个验证 Agent"（确认项 5 已批准）**应限定为"同级的独立条目可并行，
  但不共享任何环境"**（独立容器、独立库、独立卷）。

### 2.2 规则 2：Docker 实例验证 —— ⚠️ 需修正，见"坑 6"

**保留**：D1/D2/D3 三档、真实容器 + 真实 PG/Redis + 真实 HTTP/浏览器流量、禁止用 sqlite/mock 替代。

**问题**：
1. "不得仅以本地单元测试通过作为验证依据"——表述太窄，没覆盖"代码检索"这个实际用到的证据类型。
2. **D3 档位在原计划里没有明确定义**。查代码：前端在开发栈是 Vite 直连，**没有 Caddy 网关**，
   CSP 只在模拟栈（D1）生效。原会话 S1-5 用的是 "D1+D3"，S1-2 用的是"D3"——但 D3 到底是什么？
   原计划只说"真实前端容器 + 后端容器 + 无头 Chromium"，**没说前端容器从哪来**
   （`shuhao07/wangsh-frontend:2.2.0` 还是 `:dev`？）。
3. **镜像来源没有在执行流程里写死**。原计划确认项 3 被批准了"允许构建 `:dev` 镜像"，
   但 §三 的执行流程里没写"什么时候用 2.2.0、什么时候用 `:dev`"。

**修正**：
- 规则 2 增加证据分类（见坑 6）；
- **D3 档位明确定义**：前端容器 = **`shuhao07/wangsh-frontend:dev`**（工作区代码构建），
  后端容器 = **`shuhao07/wangsh-backend:dev`**，网关用 Caddy 配置；
- 在 §三 开头写死镜像选择矩阵：

| 验证对象 | 镜像标签 | 说明 |
|---|---|---|
| 已发布修复的历史回归（S1 六项） | `2.2.0`（发布镜像） | 验证的是"发布版本是否真的修了" |
| 工作区未提交改动 | `:dev`（本地构建） | 验证的是"当前代码是否正确" |
| 跨两项（如 S1-1 改后复验） | `:dev` | 改了代码就必须用 `:dev` |

### 2.3 规则 3：多 Agent 交叉验证 —— ⚠️ 需补两条

**保留**：A 执行 → B 独立重跑 → 主控判定；B 的职责是证伪；结论不一致不得多数票通过。

**补充**（对应坑 2、坑 1）：
- **规则 9**：复核 Agent 每条"新问题"必须附最小复现步骤，主控亲自复现后才生效。
- **检查项清单前置冻结**（规则 8）。
- 原计划"复核 Agent 必须覆盖全部条目，不得只抽查"——**执行时证明不可行**：
  原会话里复核 Agent 只复核了 S1-1 一项（因为它是唯一有争议的），其余 6 项直接采用了验证 Agent 结论。
  这不是偷工，而是**规则本身没有区分"有争议项"和"无争议项"**。

**修正**：规则 3 改为：
- 每个条目**至少**经过一次独立复核；
- **有争议/有改动的条目必须全量复核**；
- **无争议且无改动的条目**（只验证已发布修复的历史回归）可以**合并复核**：
  一个复核 Agent 在独立环境重跑该批全部检查项的关键断言即可，不需要逐项建环境；
- 复核 Agent 的工作量控制在**同级总工作量的 40% 以内**，超出说明验证 Agent 的检查项设计有问题。

### 2.4 规则 4：通过的定义 —— ✅ 保留，补一处

**保留**：可证伪表述、必须列出未覆盖场景/假设/残余风险、不得用"保证没问题"。

**补充**（对应坑 7）：
- 原始证据与最终判定**分离存放**；
- 判定只能**引用**证据，不能修改证据；
- 增加"**证据可重放**"要求：验证报告里的每条证据必须能被另一个 Agent 用同样的命令重放出来，
  否则该证据降级为"观察记录"。

### 2.5 规则 5：验证闭环 —— ⚠️ 需修正，见"坑 3"

**保留**：复现 → 修复 → 回归测试 → Docker 验证 → 独立复核 → 文档同步。

**修正**：
- 增加"**修复即回归**"：任何代码改动后，该级**全部**检查项重跑，旧结论作废；
- 增加"**检查项基线先于修复**"：修复前必须先实测一次当前状态作为基线（证明"修之前确实坏"），
  否则无法证明修复有效。原会话 S1-1 做得对（用 `HEAD~1` 复现 0 字节），这条应写进规则。

### 2.6 规则 6：环境安全 —— ⚠️ 需补两条

**保留**：不碰开发栈/生产、临时专用库（库名含 test/testing/ci）、独立卷与 loopback 端口、临时文件用完即删。

**补充**（对应坑 8）：
- 开发栈里创建的任何测试数据必须给出**清理确认查询**；
- 软删除必须显式说明并征得同意；
- 增加"**端口唯一性**"：一次验证一个端口，用后释放，不得复用端口掩盖端口冲突问题
  （原会话用了 15439、15449、15470 三个端口，说明每次新建是对的）。

### 2.7 规则 7：不覆盖他人改动 —— ✅ 保留，补一处

**保留**：前后 `git status` 对比。

**补充**：当前工作树有 **17 个未提交文件**，其中 `scripts/deploy.sh`、`DEPLOY.md`、`TEST_STATUS.md`
是**原会话的改动**（属于本次验证任务的一部分），而 `start-dev.sh`、前端文件是**上一轮未完成的改动**，
**两者不能混为一谈**。规则 7 需要明确：**验证开始前先给每个未提交文件打标签**
（"本次任务负责" / "只读引用" / "与本任务无关"），写进报告。

**S1-1 待复验的具体原因**（来自原会话复核 Agent + 主控复现）：

当前 `restore-db` 修复存在以下**未解决问题**（代码审查确认，位于 `scripts/deploy.sh:970-995`）：
