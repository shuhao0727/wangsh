## AUTH-02 设计检查点（2026-09-08，仅设计，未实施）

> 以下保留设计阶段的时间点结论，“未实施/不生成迁移”指该历史阶段；当前隔离候选状态以上节为准，正常服务仍未应用。

### 已确认边界

- 基线仍是当前 AUTH-01 修复后的工作区；不重做 FE-04/AUTH-01/BIZ-04，不触碰并行 XBK。
- 串行同 IP 替换后旧 refresh 恢复、A→B→A、缓存缺失、旧 IP 绑定及写入失败已用合成隔离链路核查；受控 guard 交错只证明读写间存在窗口，不证明 PostgreSQL 并发锁行为。具体运行结果和本地配置快照只维护 TEST_STATUS。
- `rotate_refresh_token` 已按用户→token 加锁并锁后重验，但它只检查 token 的过期/撤销与用户状态；刷新端点随后从 cache 读取**当前** nonce，没有比较 refresh 发行时所属代次。给 refresh 套上“最新 nonce”不是恢复原会话，而是把旧凭据提升到新代次。
- IP 绑定中的 nonce 当前未参与被替换对象校验。A 从 IP1 重登 IP2 后，IP1 的旧绑定仍可能使 B 在 IP1 登录时误踢 A 的 IP2 新会话。不能只在现有位置无条件增加“撤销 old_uid 的全部 refresh”。

### 必须保持的不变量

1. refresh 只能延续其**发行时的会话代次**；被替换代次不能通过缓存丢失、刷新、迟到回调或重放重新变为当前代次。
2. 主动登录创建新代次，普通 refresh 继承同代次；logout/被替换使旧代次失效。已完成的新登录不能被引用旧绑定的动作撤销。
3. 当单 IP 单账号策略开启时，只有当前有效的 `(IP, user_id, epoch)` 绑定才能触发替换；旧 IP、旧 epoch 的绑定仅是可清理残留。策略关闭不应引入跨用户互踢。
4. 存储失败不签发未经持久确认的有效凭据；cache miss 与缓存故障不能不经权威校验直接建立新会话。已经发出的业务写入不因撤销而回滚。
5. 登录、刷新、退出统一锁序；不得持有当前用户锁后，再随意按请求顺序获取另一个用户锁。

### 方案比较与建议

- **不采用：只读取 IP binding 拒绝 refresh**。旧绑定可过期/写失败/与当前代次不符；策略关闭、不同 IP 和代理语义也不同，不能作为发行代次证明。
- **不采用：在当前 guard 无条件撤销 old_uid 全部 refresh**。既有链路只锁登录用户，缺少旧用户锁及绑定重验，可能误伤新登录或形成反向锁等待。
- **可选的限定补丁：refresh 持久化 nonce/epoch 并与 cache 相等才刷新**。必须在缺失/故障时拒绝恢复，否则问题仍在；这会把缓存保留时间变成刷新寿命边界，改变长期 refresh/Redis 重启体验，且仍未解决跨用户原子替换和陈旧绑定。不能当作完整方案静默上线。
- **建议的完整方向：DB 持久代次为权威，Redis 仅加速**。在用户或独立会话记录上保存当前 epoch，refresh 行绑定发行 epoch，IP 绑定保存 `(规范化 IP, user_id, epoch)`。精确字段/表名待 schema 评审，不在本轮创建。JWT `sn` 可继续承载 opaque epoch；缺少有效代次的 legacy token 过渡须单独决定。
- 普通 refresh 在用户→token 锁内比较 token.epoch 与权威 epoch，锁后重验用户状态、过期和撤销；轮换保留原 epoch，不能生成或收养新 epoch。cache 缺失时仅从已确认的 DB epoch 重建，不依据旧 token 自创代次。
- 严格即时失效要求请求守卫验证权威 epoch；若只信任可能陈旧的正向缓存，DB 撤销后旧 access 仍有窗口。可先 DB 校验再用 cache 做其他读取，但增加 DB 负载；若改选有界失效窗口，必须另经策略确认，不能称为即时撤销。Redis 发布不能成为授权的唯一事实。

### 拟议锁序与事务（需专用 PostgreSQL 验证）

1. 凭据初验后，登录先按规范化目标 IP 取得 **transaction-scoped** 串行化锁（advisory lock 候选；不可用 Python 进程内锁代替）。任何写 IP binding 的入口都遵循同一协议；策略关闭时的映射写入及开关切换也须明确，不允许半数 writer 绕开锁。
2. 在 IP 锁内读取旧绑定，形成新/旧用户 ID 集合，按升序逐行取得用户锁。现有 login 在调用 guard 前已持有新用户锁，实施时必须整体重构获取顺序，不能在 guard 内追加锁冒充符合协议。
3. 锁后重验当前用户状态、旧绑定的 user_id/epoch 和旧用户权威 epoch。绑定陈旧时不撤销旧用户的新代次；有效替换才失效旧代次。将新 epoch、refresh 及目标 IP binding 在同一 DB 事务提交后才返回凭据。
4. 最后处理需要锁定的 token 行；login/logout 批量处理遵循统一顺序。refresh 和不修改 IP binding 的 logout 只取用户→token 锁，不在持有用户锁后追加 IP 锁。若 logout 要即时删 IP binding，必须重新采用 IP→有序用户→token 的完整协议；否则留下带旧 epoch 的残留，后续只允许条件清理。
5. 不主动跨 IP 清理无关映射，可避免锁多个 IP；旧映射必须以 epoch 判断是否有效，清理须比较完整旧版本。不得仅依赖 cache TTL 推断单 IP 权属：绑定寿命、会话寿命及刷新延长必须有一致合同，否则 TTL 到期又会留下两个有效用户。
6. DB 失败回滚；cache 写失败不覆盖权威状态，返回策略依守卫能否安全回源而定。DB 提交成功但响应丢失不应恢复旧代次。锁超时、死锁重试必须有界且重跑整个事务并重新校验，不能重复提交部分撤销；本轮未实现或验证调度。

锁序依据为 PostgreSQL 官方 Explicit Locking 文档的 Deadlocks / Advisory Locks 节：多对象保持一致顺序，事务级 advisory lock 随事务结束释放。该通用规则不是本项目并发验收证据。外部参考：https://www.postgresql.org/docs/current/explicit-locking.html

### 迁移、兼容与回滚门槛

- 若采用持久代次与权威 IP binding，涉及正式字段/表/索引，必须 Alembic；本轮只提出影响，不生成或运行迁移，不修改 AUTH 开关。
- 历史 refresh 无法可靠反推出发行 nonce；不可全部回填成当前 epoch，否则重新授权本应失效的凭据。建议明确一次重新登录窗口；如需兼容期，要书面限定旧格式截止和风险。
- 新旧版本混跑期间，旧 writer 不校验 epoch 会破坏不变量；须先兼容 schema、再协调 writer/reader 切换，不可仅滚动一半服务。停用、改学号/密码、角色变更等 AUTH-04 生命周期仍独立待确认。
- 回滚不能恢复已撤销凭据：备份/恢复验证、拒绝旧格式的安全模式、必要的全员重新登录与失败回退都须评审。不得通过直接 drop epoch 字段、复原旧 token 表来假装无损回退。
- 开关开启可能影响共享 NAT/机房多人同 IP；本方案修复既有语义，不擅自启用或扩大该策略。代理可信来源和转发头清洗须独立验收。
