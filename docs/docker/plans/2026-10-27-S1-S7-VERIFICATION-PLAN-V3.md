## 四、规则（10 条）

写入 `docs/ENGINEERING_GOVERNANCE.md` §十二。

1. **分级驱动**：S1→S7 固定顺序，同级内串行，不同级不共享环境。
2. **Docker 实例验证**：
   - 三档：D1 全栈模拟（`deploy.sh simulate`）、D2 组件实例（一次性 PG/Redis + 真后端）、D3 页面实例（`:dev` 前端 + `:dev` 后端 + Caddy + headless Chromium）。
   - 证据分三类：**实例检查项**（必需）、**代码检索**（只证明"已删除"，不证明"行为正确"）、**单元测试**（只作前置筛查）。
   - 每个有行为的条目至少有一个实例检查项。
   - 纯文档/纯配置条目豁免 Docker 验证，验证方式为门禁 + 文档合同检查，适用豁免的条目须逐条列出。
   - 镜像选择：验证已发布修复用 `2.2.0`；验证工作区代码用 `:dev`；改过代码后复验一律用 `:dev`。
3. **多 Agent 交叉验证**：
   - 每个条目至少一次独立复核。
   - 有代码改动或有争议的条目**全量复核**。
   - 无改动无争议的条目可合并复核（一个 Agent 在独立环境重跑关键断言）。
   - 复核 Agent 工作量不超过同级总量的 40%。
   - 结论不一致不得多数票，必须找根因重跑。
4. **通过的定义**：
   - 通过 = 冻结清单中全部检查项符合预期 + 独立复核一致 + 报告列出未覆盖场景、依赖假设、残余风险。
   - 原始证据与最终判定分开存放；判定只引用证据，不改写证据。
   - 证据必须可被另一个 Agent 用同样命令重放，否则降级为"观察记录"。
   - 禁止"保证没问题""不可能出错"这类表述。
5. **验证闭环**：
   - 顺序：基线实测 → 复现缺陷 → 修复 → 回归测试 → Docker 验证 → 独立复核 → 文档同步。
   - **修复即回归**：任何代码改动后，该级全部检查项重跑，旧结论作废。
   - 基线先于修复：修复前必须实测一次"修之前确实坏"。
6. **环境安全**：
   - 不碰开发栈容器运行状态与生产环境。
   - 数据库用临时专用库，库名含 `test/testing/ci`，用完即删。
   - 测试容器独立名称、独立卷、loopback 端口，用后删除。
   - 开发栈里造的测试数据必须给出清理确认查询；软删除要显式说明并征得同意。
7. **不覆盖他人改动**：
   - 开始前记录 `git status`，结束时只允许增加预期改动。
   - 每个未提交文件打标签：`本次负责` / `只读引用` / `无关`。
8. **检查项清单前置冻结**：清单先写入文件再执行，只能追加。
9. **复核结论附最小复现**：复核 Agent 每条新问题附最小复现命令、预期输出、实际输出；主控亲自复现后才生效，未复现的标注"主控未能复现，待补前提"。
10. **链式改动作为单一验证单元**：有调用或数据依赖的改动文件同批验证，按链路最高 S 级判定，不得拆到不同级别分别通过。
