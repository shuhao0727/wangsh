# 热点问题归类 Agent — 指令文档

本文维护热点问题分析中 LLM 归类的当前合同。实现位于
`backend/app/services/agents/hot_agent.py`，流式入口为 `POST /ai-agents/analysis/hot-questions/stream`。

## 目标

热点问题只回答一个问题：**教师提问附近，学生是在回应教师，还是生成了教师没问过的新问题。**
完整的“教师思路 vs 学生思路”对照属于学生问题链，不在本 Agent 范围内。

LLM 只做逐条语义判断；所有计数、按教师提问分阶段、按时间分桶都由程序完成，避免模型数数出错。
本 Agent 不输出 Bloom 分层、主题诊断、教学建议或执行摘要。

## 输入

| 内容 | 来源 |
|---|---|
| 教学设计 / 任务单 | 生成分析时第 2 步填写的任务单，截断到 3000 字 |
| 教师提问 T1、T2…… | 第 2 步的“教师提问标记”和教师账号的提问，按时间先后编号 |
| 学生问题 | 通过质量筛选、带 `message_id` 的学生提问，每条截断到 300 字 |
| 教师补充说明 | 提示词模板或自定义指令（可选） |

学生问题按每批 60 条分批调用，单批失败不影响其他批次。

## 归类体系

| 大类 | 细分 | 含义 |
|---|---|---|
| `response` 回应型（必须指向某个 Tn） | `clarify` 理解追问 | 没理解教师的问题，在问概念、问意思 |
| | `apply` 尝试应用 | 按教师的问题动手写代码、套用方法 |
| | `debug` 调试求助 | 照着做出了错，在问报错或结果不对 |
| | `verify` 核对确认 | 已有答案，在确认对不对 |
| `generative` 生成性（不指向 Tn） | `principle` 原理深挖 | 追问为什么、背后的原理或机制 |
| | `transfer` 迁移拓展 | 换场景、换数据、推广到别的情况 |
| | `new_confusion` 新的困惑 | 暴露教学设计没覆盖到的卡点或误解 |
| `unrelated` 无关 | — | 闲聊、测试、问候，或与本节课内容无关 |

生成性的定义是：**与本节课内容有关，但不在回应任何一个教师提问**。判断以教学设计和教师提问的语义为准，
不看关键词；时间只作参考，学生在 T2 之后问的仍可能是在回应 T1。

提示词要求模型**先看内容、再看时间**：判定为回应型前必须能说清教师提问里明确要求过这一点，
只要教师提问没有涉及，即使时间上紧接该提问也归为生成性；拿不准回应型与生成性时选生成性，
避免把学生的真实盲区误判成“在回应教师”。提示词内附五条来自实际误判的反例，改提示词时须保留。

归类调用显式传 `temperature=0` 以减少随机性，但**不是所有上游都严格执行该参数**，结果仍可能有波动。

## 多次投票

每条问题默认判定 `VOTE_ROUNDS = 3` 轮（上限 `MAX_VOTE_ROUNDS = 5`），逐批进行：同一批先跑完各轮再处理下一批。

- **大类取多数票。** 一致票数达到 `CONFIDENT_SHARE`（2/3）才算确定；恰好 2/3 算确定（判断为 `<`）。
- **没有严格多数才标待确认。** 3 轮里 2 次生成性、1 次回应属于有严格多数，取生成性、一致度记 0.67；只有出现并列最高票（如三类各一票）时 `ambiguous = true`，**不计入任何类别**，统计里归入“未归类”，页面显示“待确认”和一致度，由老师回看原话判断。不为了凑出结论而硬选。
- **细分与教师引用同样取多数，平票时留空。** 并列最高票时返回 `None`（不按出现顺序任选一个）；大类确定而细分平票时，该条仍计入回应总数与对应 Tn，但不归属任何细分子项。
- **教师提问先去重再编号。** 自动识别的教师提问带 `message_id`，老师手填的没有。同一 `message_id` 只留一条；手填内容与自动识别相同且时间相差不超过 `MANUAL_MERGE_SECONDS`（120 秒）时视为同一条并保留自动识别那条，否则学生的回应会被拆到两个 Tn 上。去重后的清单随结果返回为 `teacher_refs`，前端据此编号。
- 每条结果附带 `agreement`（一致度）、`ambiguous`、`votes`；批次整体还有 `vote_rounds`、`ambiguous_count`（待确认，多轮无共识）与 `unlabelled_count`（模型没有返回结果）。两者都计入 `totals.unclassified`，但分开统计，便于判断是模型漏答还是判定不稳。
- 代价：API 调用次数是单轮的 `VOTE_ROUNDS` 倍。学生问题较多时会明显增加耗时与费用。

实测（同一份 21 条数据）：单轮时三次结果的回应数在 11–14 间跳动；改成 3 轮投票后，「为什么下标从 0 开始」「列表要写在 input 后面还是前面」等条目稳定，但仍有个别条目（如“刚才的圆括号问题我还没搞懂”）在 2:1 之间摇摆，会被标为低一致度而不是静默给出错误结论。

## 输出与校验

模型输出 `{"items": [{"id", "category", "subtype", "teacher_ref", "reason"}]}`。程序逐条校验，
以下情况整条丢弃，计入“未归类”，不做猜测修补：

- 大类不在上表，或细分不属于该大类
- 回应型的 `teacher_ref` 不是本节课存在的 Tn
- `id` 不在本批输入中，或同一 `id` 重复（只取第一条）

生成性与无关的 `teacher_ref` 一律置空，无关的细分置空。

## 保存结构

分析结果的 `question_classification` 字段：

- `items`：按 `message_id` 索引的逐条标签与一句判断依据
- `totals`：回应、生成性、无关、未归类的条数
- `subtypes`：各细分条数
- `teachers`：每个 Tn 的时间、原文、回应条数与细分
- `batch_count` / `failed_batch_count`

`classification_status.status` 为 `completed`、`partial`（部分未归类）、`empty`（全部失败）或
`skipped`（未配置分析智能体）。后三种情况下前端明确提示，生成性退回关键词估计，不冒充智能体结论。

## 前端呈现

- 时间图按“回应教师 / 生成性 / 无关 / 未归类”堆叠，点击各段筛选该类原问，每条显示判断依据。
- “按教师提问分阶段”从每个 Tn 开始到下一个提问为止，列出回应本题的细分条数、仍在回应更早提问的条数，
  以及本阶段全部生成性问题原文——这是观察学生思路的重点。
- Markdown 导出附带分阶段结果与生成性问题原文。
